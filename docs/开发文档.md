# 开发文档

## 1. 范围与原则

PyForge 首版交付一个在 RTX 4080 SUPER 上可复现的 Python 编程助手 SFT 流程。先验证 1.5B 模型与高质量数据，再考虑模型扩容。本文包含开发设计与后续目标；当前已实现数据校验、编码、QLoRA 训练、完整恢复、最佳检查点选择和单次推理。可执行 JSON 配置与命令见[训练运行指南](训练运行指南.md)。4060 已实测，4080 SUPER 正式实验待执行。

优先保证：数据可追溯、显存可控制、训练可恢复、结果可比较。训练损失下降不能单独作为模型能力提高的证据。

## 2. 模块设计

| 计划模块 | 职责 | 主要输出 |
| --- | --- | --- |
| `data` | 校验、清洗、去重、分组划分、统计 | 训练/验证/测试 JSONL、数据清单 |
| `training` | 模型加载、分词、标签屏蔽、SFT、断点恢复 | LoRA 适配器、检查点、日志 |
| `evaluation` | 固定生成策略、代码提取、隔离执行、指标汇总 | 样例预测、JSON 与 Markdown 报告 |
| `inference` | 加载固定基础模型与适配器，处理多轮对话 | 本地 CLI 回答 |
| `utils` | 配置校验、随机种子、运行清单、路径管理 | 可追溯运行元数据 |

数据流：原始语料 → 校验和去重 → 按来源分组划分 → 模板编码 → SFT → 适配器 → 固定评估 → 本地推理。

## 3. 环境与依赖管理

优先在 WSL2 / Linux 环境开发。记录操作系统、Python、GPU、驱动、PyTorch、CUDA 运行时以及全部训练依赖版本。首次端到端验证成功后，提交项目依赖配置和锁定文件，避免将所有包简单升级到最新版。

环境验证必须覆盖：CUDA 可用性、BF16 支持、4-bit 模型加载、可训练参数数量、一次反向传播，以及适配器保存后重新加载。训练失败时输出清晰诊断，不能静默切换到 CPU 训练。

## 4. 起始训练配置

以下 YAML 是设计示意，不能直接传入 CLI。当前可执行配置采用扁平 JSON，位于 `configs/`，由 `training_config.py` 检查类型和取值；量化、BF16、batch 1、梯度检查点等策略由训练实现固定。

```yaml
model:
  name: Qwen/Qwen2.5-Coder-1.5B-Instruct
  revision: null                 # 正式运行必须填入实际解析出的 commit SHA
quantization:
  load_in_4bit: true
  quant_type: nf4
  double_quant: true
  compute_dtype: bfloat16
lora:
  r: 16
  alpha: 32
  dropout: 0.05
  target_modules: [q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj]
training:
  max_seq_length: 2048
  per_device_train_batch_size: 1
  gradient_accumulation_steps: 16
  gradient_checkpointing: true
  learning_rate: 0.0001
  num_train_epochs: 2
  warmup_ratio: 0.03
  lr_scheduler_type: cosine
  weight_decay: 0.01
  max_grad_norm: 1.0
  seed: 42
  packing: false
  assistant_only_loss: true
  eval_steps: 100
  save_steps: 100
  save_total_limit: 2
```

单 GPU、无 packing 时，有效 batch 为 `1 × 16 = 16` 条样本；不同长度样本的 token 数仍然不同。学习率与训练轮次只是初始值，根据验证集调整。短于 100 步的冒烟运行必须在结束时额外评估并保存。

量化训练前按 PEFT 要求准备模型，并验证目标模块名称真实存在。冻结基础权重，仅允许预期的适配器参数参与训练。启用梯度检查点时按框架要求处理 `use_cache`。

使用模型自身 chat template，避免手工拼接不匹配的特殊 token。`assistant_only_loss` 是行为要求：实现时必须检查模板是否支持 assistant token mask；若不支持，构造并测试等价标签屏蔽，不能仅设置一个标志就认为已生效。

## 5. 显存管理

16 GB 是设备容量，不等于全部可用于训练。激活、优化器状态、临时计算缓存、桌面占用与序列长度都会影响峰值；4060 的 0.5B 冒烟实测峰值 allocated 约 1.52 GiB、reserved 约 3.41 GiB，详见[训练验证记录](训练验证记录.md)，不能外推为 1.5B 的显存需求。

冒烟阶段记录峰值 allocated / reserved 显存、非 padding token 吞吐和单步耗时。建议留出约 1–2 GB 余量，此数值是运行目标而非适配保证。

出现 OOM 时依次检查其他 GPU 进程、确认 micro batch 为 1 和梯度检查点已启用、将序列长度从 2048 降到 1024，再降低 LoRA rank 或缩小目标模块范围。梯度累积主要用于恢复有效 batch；在 micro batch 已为 1 时增加累积步数不能解决单样本激活过大的问题。调整后使用新的运行 ID 并记录配置变化。

## 6. 训练与恢复

每次运行记录唯一 ID、代码提交 SHA（以及工作区是否有未提交修改）、依赖版本、基础模型与 tokenizer revision、数据哈希、划分清单、配置、种子和硬件信息。不得把访问令牌写入日志。

先用 50–100 条合法样本跑 10–20 个更新步，检查 loss 有限、assistant 标签非空、基础权重被冻结、检查点可重新加载。正式训练先从约 1,000–5,000 条清洗样本验证方向，再按评估结果扩充数据；该数量属于实验计划。

断点恢复必须恢复优化器、调度器、步数与随机状态；仅加载适配器权重属于继续微调，不属于完整恢复。推理适配器与用于恢复的训练检查点分别管理。验证集用于检查过拟合和选择检查点，测试集只用于最终比较。

## 7. 产物与推理

每次发布至少包含适配器权重、适配器配置、tokenizer/模板引用、基础模型精确 revision、完整配置、数据清单、环境清单及评估报告。默认不合并基础模型，推理时同时加载基础模型与适配器。

合并权重属于可选后续功能，需重新确认精度、内存和许可证，不能把 4-bit 训练加载直接视为通用合并流程。CLI 应支持最大输入长度、最大生成 token 数和清空历史；超长输入应明确提示，不能无提示截掉关键代码。

## 8. 开发里程碑与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| M0 环境 | 依赖锁定、GPU 自检 | 成功加载、反传、保存与重载 |
| M1 数据 | 数据管线、质量报告 | 格式合法、来源可追溯、跨集合无已知重复 |
| M2 基线 | 原始模型评估结果 | 固定题集、生成参数及执行环境 |
| M3 训练 | QLoRA 训练与恢复入口 | 冒烟通过、正式训练可追溯且无 OOM |
| M4 评估 | 基础/微调对照报告 | 达到数据与评估规范中的门槛 |
| M5 使用 | 本地 CLI、运行指南 | 全新进程可加载适配器并回答示例任务 |

## 9. 测试与提交约定

单元测试重点覆盖数据校验、分组划分、截断和标签屏蔽；集成测试覆盖训练后保存与重载。GPU 测试显式标记，避免在无 GPU 环境误报通过。

`.gitignore` 已忽略虚拟环境、缓存、模型权重和训练输出；当前数据集与必要的检查报告提交 Git，以便跨机器同步。配置变动需说明对显存、数据或评估可比性的影响。训练进程与生成代码执行器使用不同环境；执行隔离要求见数据与评估规范。
