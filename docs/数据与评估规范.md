# 数据与评估规范

## 1. 数据目标

首版围绕 Python 函数和单文件任务，建议起始比例为：代码生成 40%、错误修复 25%、代码解释 15%、测试生成 15%、代码改进 5%。这是采样目标，实际分布须在数据报告中记录。

中文需求优先，同时保留部分英文与混合语言样本。统一目标 Python 版本为 3.11，首批优先标准库任务，第三方依赖必须明确记录。

## 2. 存储格式

使用 UTF-8 JSONL，每行一个完整 JSON 对象。下面是**单条记录的展开示例**，落盘时须压成一行：

```json
{
  "id": "pygen-000001",
  "task_type": "code_generation",
  "language": "zh",
  "source": "self_authored",
  "license": "self_owned",
  "group_id": "sum_even_family_001",
  "messages": [
    {"role": "system", "content": "你是 Python 编程助手，提供正确、清晰、可运行的代码。"},
    {"role": "user", "content": "编写 sum_even(numbers)，返回整数列表中偶数的总和，空列表返回 0。"},
    {"role": "assistant", "content": "```python\ndef sum_even(numbers: list[int]) -> int:\n    return sum(n for n in numbers if n % 2 == 0)\n```"}
  ]
}
```

必填字段为 `id`、`task_type`、`language`、`source`、`license`、`group_id`、`messages`。`self_owned` 仅表示本示例的自有来源声明，实际数据必须记录具体授权依据。外部数据额外记录原始链接、数据集版本和获取日期；存在归属要求时保留作者信息。

`messages` 的 role 允许 `system`、`user`、`assistant`，system 若存在只能在开头，对话应按 user/assistant 交替且以 assistant 结束。首版不接收 tool 消息。内容必须为非空字符串，至少有一组 user/assistant。训练前移除元数据字段，仅将 messages 交给模板编码。

## 3. 清洗与编码

1. 验证字段、唯一 ID、角色顺序、编码和来源许可。
2. 移除个人信息、密钥、无效片段、乱码与明显错误答案。敏感数据应删除或替换为合成样本。
3. 对代码生成和修复样本做语法检查；在隔离环境执行可获得的测试。不能把语法通过当作正确性证明。
4. 对题面、代码和来源标识执行精确及近似去重，记录去重规则与版本。
5. 使用固定 tokenizer 与 chat template 统计 token 长度，再划分、编码。
6. 超长样本首版直接过滤并统计原因，避免截断函数体或删除全部回答。后续如采用截断，须定义保留策略并测试。

训练标签仅覆盖 assistant 回答及模板约定的结束标记；system、user、padding 的标签设为 `-100`。多轮对话可以训练所有 assistant 回合，策略须保持一致。编码后必须确认每条样本至少有一个有效监督 token。

首版关闭 packing；未来开启时须验证样本边界、注意力与标签行为，并单独记录实验。

## 4. 数据划分与泄漏控制

建议按 90% / 5% / 5% 划分训练集、验证集与测试集，种子为 42。以 `group_id` 为最小划分单位：同一题目的改写、同一代码来源或仓库的近似样本必须在同一集合。按组划分后比例允许偏差，需报告实际条数、token 数、任务与语言分布。

先完成分组和去重，再生成固定划分清单。测试集冻结后不得用于调参、筛选训练数据或生成训练题。公开基准可能已出现在基础模型预训练中，不能仅凭公开基准成绩声称对新任务的泛化提升。

## 5. 评估集合与执行

建立至少 100 道独立、人工检查过的内部测试题，其中建议至少 60 道有可执行测试。剩余题评估解释与测试生成等能力。为可执行题提供函数签名、输入约束、期望行为及隐藏测试；覆盖空输入、边界值、异常和常见类型。

基础模型与微调模型使用相同的提示、题集、tokenizer、模板、运行环境与生成设置。首轮采用贪心生成（`do_sample=false`），统一 `max_new_tokens=512`，每题生成一次；超过上限导致不完整的回答记为失败。后续改变生成上限须对两个模型重新评估。

代码提取优先取唯一 Python fenced code block；没有代码块时尝试将完整回答作为代码；存在多个候选块、无法解析、语法错误、执行异常或超时均记为失败，并保留原因。此规则需实现为独立、可测试的组件。

生成代码属于不可信输入，必须在独立、非特权、禁网的执行环境中运行，不挂载用户目录或训练密钥，设置 CPU、内存、进程与时间上限。默认每题 5 秒，具体额度随题集冻结。Python 子进程加超时不构成完整隔离；未具备隔离执行器时，只能输出静态评估，不能报告执行通过率。GPU 训练环境不承担代码沙箱职责。

## 6. 指标与验收门槛

| 指标 | 口径 |
| --- | --- |
| 单次生成测试通过率（pass@1） | 全部隐藏测试通过的题数 / 所有可执行题数；提取失败与超时计入分母 |
| 语法通过率 | 可编译代码的题数 / 要求输出代码的题数 |
| 分任务表现 | 按代码生成、修复等类别分别统计通过率与失败原因 |
| 人工质量分 | 对正确性、需求遵循、解释清晰度分别按 1–5 分盲评 |
| 资源指标 | 峰值显存、训练 token/s、推理生成 token/s 与测量条件 |

默认首版验收目标为：冻结内部测试集的 pass@1 比基础模型提高至少 **5 个百分点**；样本数不少于 20 的各个可执行任务类别，下降不得超过 **5 个百分点**；人工质量均分不低于基础模型。报告同时列出题数和通过数，小样本改进应明确标为初步证据，有条件时补充配对置信区间。

若未达到门槛，保存实验并分析数据或配置，不能将“训练成功”写成“能力提升”。验收目标的修改必须发生在查看该轮测试结果之前，并记录理由；验证集可以用于日常迭代。

## 7. 报告与复现

每份报告记录：运行 ID、代码与模型 revision、数据版本与哈希、评估题集版本、适配器路径、生成参数、依赖和硬件、指标分母、逐题结果及失败样例。人工评分同时保留评分准则与评分人数。

交付时分别保存：适配器、恢复检查点、机器可读指标、可读评估报告。外部发布数据或预测样例前重新检查许可与隐私，报告不得包含访问令牌或原始个人信息。
