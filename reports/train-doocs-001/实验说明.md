# train-doocs-001 实验记录

本目录为真实完成的 0.5B QLoRA 实验轻量归档，可随 Git 同步。它不是模型分发包，不包含适配器、基础权重或完整恢复检查点。

## 训练结果

- 数据：训练 2,292、验证 129，留出 123；对应文件 SHA 在 run_manifest.json 中。
- 配置：2048 token、rank 8、梯度累积 4、2 轮、1,146 个优化器更新步；精确配置记录在 run_manifest.json 的 config 字段。
- 最佳检查点：checkpoint-1100，验证损失 0.3515698。
- 最终 eval_loss 是 Trainer 重载最佳已保存检查点后计算的，不表示最后一步权重优于所有历史检查点。
- 总耗时约 4,847 秒；PyTorch peak allocated 约 4.47 GiB。peak reserved 记录为 14.19 GiB，该计数不应直接当作设备专用显存容量或其他机器的容量保证。
- 源代码提交与脏工作区标记、模型 revision、版本与硬件使用原运行清单的真实值，未改写成归档时的状态。

## 执行结果

微调模型 20 题中通过 10 题（50%）、答案错误 7 题（35%）、runtime_error 3 题（15%）。每题全部本地用例通过才计为通过，原始回答均未因 token 上限截断。后续已生成同条件基础模型答案并执行：通过 12 题（60%）、答案错误 6 题、runtime_error 2 题。

### 同题逐项对照

基础模型使用同一基础模型 SHA、tokenizer、system、题面、1024 token 贪心解码、同一 Docker 镜像和 10 秒预算。微调模型复用原来未经修改的 20 条回答；没有挑选或重写答案。基础模型原始预测、生成清单和报告为 baseline_predictions.jsonl、baseline_predictions.manifest.json、baseline_evaluation.json。

配对结果：2 题改善、4 题退步、8 题均通过、6 题均未通过。改善为第 69、136 题；退步为第 9、17、121、169 题。本轮净下降 10 个百分点，不能声称有效提升；样本仅 20 题，仍不宜外推全部编程任务。

表格及完整原始回答见[逐题对比](comparison/逐题对比.md)、[可展开答案](comparison/逐题答案对比.html)和 comparison/模型评估对比.xlsx。comparison.json 记录来源 SHA 和共同条件，files_manifest.json 核对各输出文件 SHA。Excel 第一表有逐题结果和汇总公式，第二表按题目并列展示题面和两边原始答案。

3 题运行错误的原始代码可见以下问题（静态定位，不是新增的异常堆栈采集）：

- 0036 有效数独：squares 建成二维列表，却用一维索引并调用 .add；元素仍为 list。
- 0169 多数元素：将计数器当作候选元素下标，return nums[cnt] 可能越界，算法本身也不正确。
- 0228 汇总区间：j 指向区间的后一位，却访问 nums[j]；末段 j 等于列表长度时越界，单元素判断也不正确。

这些问题集中在算法状态与边界处理，不是 Docker 环境失败，也不是回答截断。保留原始代码，不通过手工修改答案提高分数。现有基线对照没有显示本轮稳定收益，不宜只增加轮数来追求更低训练损失。

Docker 启动后可对归档预测重新执行，不必重新加载模型：

```powershell
pyforge evaluate --suite datasets/benchmarks/doocs-leetcode/executable_v1.jsonl --predictions reports/train-doocs-001/predictions.jsonl --report outputs/doocs_finetuned_report_v1.json --timeout 10
```

如 outputs 下已存在同名报告，请换新路径。未来将执行结果归档时请使用新的目录，例如 reports/train-doocs-001-evaluated，并带 --evaluation 参数；不要覆盖或改写本次归档。
